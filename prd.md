## What We're Building

**Forkcast** — an AI-powered meal intelligence web platform.

The core idea: a user inputs what's in their pantry, and Forkcast recommends personalized recipes, tracks their nutritional intake, adapts their meal plan dynamically when life happens (cheat meals, skipped meals), and generates a shopping list to fill the gaps.

### The 5 Core Features (MVP Phase 1)
1. **Pantry Inventory Management** — user maintains a live list of ingredients with quantities
2. **AI Recipe Recommendations** — 3 options per meal slot, generated by an LLM using pantry + user profile + macro budget, nutrition-verified via Spoonacular API
3. **Nutritional Tracking** — log meals, track daily/weekly macros (protein, carbs, fat, calories, fiber)
4. **Adaptive Meal Plan Rebalancing** — when user logs a cheat meal or skips a meal, the system recalculates remaining meals for the day/week to keep them on track
5. **Shopping List Generation** — auto-diff between meal plan requirements and current pantry

### Out of Scope for Phase 1 (don't suggest or add these)
- Barcode scanner
- Mobile app
- Fitness integration
- ML recommendation model (Phase 2 — LLM handles recommendations now)
- Cultural/genomic dietary profiling (Phase 2)
- Social features

## Agreed Tech Stack

| Layer | Technology | Why |
|---|---|---|
| Frontend | React + Vite + TailwindCSS | Industry standard, component-based, good for learning |
| Backend | FastAPI (Python) | My strongest area, async-native, clean |
| AI Layer | LangChain + OpenAI or Anthropic API | Prompt orchestration, structured output, swappable |
| Nutrition Data | Spoonacular API (free tier) | Recipe lookup, verified macro/micro data |
| Primary DB | PostgreSQL | Relational data, ACID transactions, foreign keys |
| Cache | Redis | Cache Spoonacular responses (150 req/day limit), sessions |
| Auth | JWT + bcrypt | Stateless auth, 24h token expiry |
| Deployment | Vercel (frontend) + Railway (backend + DB + Redis) | Simple, git-connected, managed infra |

## System Architecture (Agreed Design)

```
[React Frontend] — HTTPS + JWT → [FastAPI Backend]
                                        │
              ┌─────────────────────────┼──────────────────────────┐
              ▼                         ▼                          ▼
        [AuthService]         [RecommendationService]      [RebalanceService]
        [PantryService]       [NutritionService]           [ShoppingListService]
              │                         │                          │
              ▼                         ▼                          ▼
        [PostgreSQL]              [Redis Cache]           [External APIs]
                                                     ┌──────────────────────┐
                                                     │  LLM API (Claude/GPT)│
                                                     │  Spoonacular API     │
                                                     └──────────────────────┘
```

### AI Pipeline (5 Steps — must follow this architecture)
1. **Context Assembly** — fetch user profile, pantry state, today's macro budget from PostgreSQL
2. **Prompt Construction** — build structured JSON prompt payload (typed fields, not freeform)
3. **LLM Inference** — call LLM, enforce structured JSON output schema, parse with Pydantic, retry once on parse failure
4. **Nutrition Enrichment** — for each recipe returned, call Spoonacular to get verified nutrition data (override LLM estimates)
5. **Ranking & Filtering** — apply hard filters (dietary restrictions, calorie cap), rank by pantry coverage %, cuisine match, goal alignment

> **Architecture note**: The LLM call in Step 3 is intentionally modular — designed to be swapped for a collaborative filtering ML model in Phase 2 once user interaction data exists. Don't tightly couple this step.

### Cache-Aside Pattern for Spoonacular
```python
cache_key = f"nutrition:{ingredient_name}"
cached = redis.get(cache_key)
if cached: return cached
result = spoonacular.fetch(ingredient_name)
redis.set(cache_key, result, ex=86400)  # 24hr TTL
return result
```

## Database Schema (5 Core Entities)

### User
```
id, email, password_hash, name, age, sex, height_cm, weight_kg,
goal (enum: weight_loss/muscle_gain/maintenance/general),
calorie_target, cultural_preference, location, dietary_flags[]
```

### PantryItem
```
id, user_id (FK), ingredient_name, ingredient_id (Spoonacular),
quantity, unit, is_low (bool)
```

### MealPlan
```
id, user_id (FK), date, meal_slot (enum: breakfast/lunch/dinner/snack),
recipe_id, recipe_name, recipe_data (JSON),
status (enum: planned/logged/skipped/deviated)
```

### NutritionLog
```
id, user_id (FK), meal_plan_id (FK), logged_at,
calories, protein_g, carbs_g, fat_g, fiber_g,
is_unplanned (bool)
```

### RebalanceEvent
```
id, user_id (FK), triggered_at, trigger_type (enum: cheat_meal/skipped/manual),
delta_calories, original_plan_snapshot (JSON), adjusted_plan_snapshot (JSON)
```

## Non-Functional Rules (enforce these throughout)
- All LLM and external API calls must use `async def` + `await` + `httpx` (not `requests`)
- Passwords: bcrypt, minimum 12 rounds
- JWT: 24h expiry, validated in middleware before routes
- LLM failures: graceful fallback to cached recommendation
- Spoonacular failures: surface error to user with retry prompt
- No business data inside JWT payload
- All secrets in environment variables: `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, `OPENAI_API_KEY`, `SPOONACULAR_API_KEY`
